Pump-history background · the next exercise

Our next learning objective is to analyze a pump’s maintenance history: identify recurring symptoms, summarize past work and outcomes, cite evidence, and distinguish confirmed findings from unresolved questions.

Implementation status: this section defines the agreed pump-history exercise. Why use an auxiliary feedwater pump?

We will use AFW-P-101A, an invented motor-driven auxiliary feedwater pump at a fictional pressurized-water reactor facility. Auxiliary feedwater supplies steam generators when normal feedwater is unavailable. NRC documents this safety-related role and examples of motor-driven pumps. Exact configurations differ between plants.

RecordDateInformation available in the record

USER QUESTION · history above supplied as context

Based on AFW-P-101A’s history, has the vibration issue recurred? What did the previous maintenance achieve, and what remains uncertain? Cite the records.

ILLUSTRATIVE WEAK ANSWER

“The bearing has failed again and should be replaced.”

Problem: the records do not confirm another bearing failure. A recurring symptom alone does not establish the same cause or justify this recommendation.

DESIRED EVIDENCE-BACKED ANSWER

The vibration symptom recurred in June after reduced vibration was recorded in February [WO-102, WO-103].

January’s record documents bearing wear and replacement. February’s follow-up supports improvement after that work, but does not establish a permanent resolution [WO-101, WO-102].

The June event’s cause is not established: inspection findings are absent, and July’s review still lists the cause as unconfirmed [WO-103, WO-104]. The history supports recurrence of the symptom, not confirmation of the same failure mechanism.

These are illustrative answers, not measured before/after outputs. A prompted base model may already answer well. A future baseline comparison must use the same supplied history and question for both models.

What would LoRA actually learn?

Historical records + question→Reviewed target answer→Train the LoRA adapter→Answer from a new supplied history

We would train on history + question → evidence-backed answer examples. The goal is a repeatable reading and reasoning behavior: connect events, cite sources, preserve uncertainty and avoid unsupported conclusions.

The current history still belongs in the prompt when the model is used. The adapter is not an up-to-date maintenance database. Later, authorized local retrieval can find the relevant records automatically. Predicting failure dates from sensor streams would require a separate modeling and validation exercise.

How would we test this richer task?

Evaluation dimensionQuestion for the evaluator
Factual correctnessDoes each claim match the history supplied to the model?
Citation correctnessDoes the cited record actually support the associated statement?
Timeline accuracyAre observations, work and outcomes in the correct sequence?
CompletenessAre recurrence, prior outcome and uncertainty all addressed?
Uncertainty handlingDoes missing evidence remain unknown rather than become a confident diagnosis?
Unsupported conclusionsDoes the model invent a cause, completed action or approval?

Split by whole maintenance episodes, not by paraphrases of the same event. Keep later findings out of questions about what was known at an earlier date. If one episode supplies several questions, keep them in the same split. A future episode test on one pump measures a narrower ability than generalization to other pumps or facilities.

Use human-reviewed expected claims and evidence IDs. Exact string matching alone cannot fairly score paraphrased historical explanations, and a valid JSON response does not establish factual correctness. Report baseline and adapter results, with representative errors, rather than relying only on training loss.

03

Understand training and LoRA · 15–20 min

Before opening Python, learn what changes inside a model, how examples drive those changes, and why we use a small adapter.

Instructor plan: 3 minutes on the model, 5 on the training loop, 5 on LoRA, and 4 on a group exercise. Allow up to 3 extra minutes for questions. No installation or coding is needed for this lesson.

0–3 minutes · What is a model?

A language model is a large mathematical function with learned numbers called weights. A tokenizer converts text into numbered pieces called tokens. Given the tokens so far, the model predicts probabilities for the next token. Repeating that process produces an answer.

Text question→Tokenizer: text to numbers→Model: next-token probabilities→Choose a token; repeat→Answer text

Tokens may be whole words, parts of words or punctuation. A model is not a database of approved answers. It can produce plausible text that is incomplete or wrong.

ActivityWhat happens to weights?Example
PretrainingLearns a broad model from a large collection of data.Learning language patterns before our workshop.
Fine-tuningUpdates selected weights using a focused dataset.Learning our record categories and JSON format.
Inference / chattingUses weights without updating them in this workflow.Classifying a new record with the saved adapter.
Local retrieval / RAGAdds retrieved source text to the prompt; does not itself train weights.Answering with passages from the current document register.

Ask: “If I correct the model in a chat, have I permanently trained it?” Answer: Not in this workshop. A correction may influence that conversation if it remains in the context, but a training program must update and save weights to make an adapter change persist.

3–8 minutes · Follow one training example

Consider a fictional reactor protection system maintenance record with a department but no work order ID:

INPUT
Reactor protection system instrumentation maintenance documentation review.
Supporting inspection report absent; independent review pending.
Department: Maintenance.
Work order ID: not supplied.

TARGET ANSWER
{"category":"maintenance_record","department":"Maintenance",
 "review_queue":"maintenance_records",
 "missing_information":["work_order_id"]}
  1. Prepare: format the system instruction, input record and correct answer as a chat, then tokenize them.
  2. Predict: during training, the model predicts each answer token using the preceding correct tokens. This is often called teacher forcing; it differs from generating an entire answer on its own.
  3. Measure: the loss penalizes low probability assigned to the correct next answer token. Our script ignores the instruction and input positions when calculating loss.
  4. Calculate: loss.backward() finds gradients—how trainable weights affect that loss.
  5. Update: optimizer.step() adjusts trainable weights. The learning rate controls the update size.
  6. Repeat: process more examples. One pass through all 60 training examples is one epoch.
Example + target→Token predictions→Loss→Gradients→Weight update

A simplified illustration: if an adapter increases the probability assigned to the correct answer tokens, their loss falls. A loss of 0.01 does not mean 99% accuracy. We evaluate full generated answers separately.

Our three epochs produce 60 × 3 = 180 optimizer updates, because batch size is one and this script does not accumulate gradients across examples. More epochs are not automatically better: the model can fit the training wording while struggling with new records.

8–13 minutes · What is LoRA?

LoRA means Low-Rank Adaptation. It adds a compact trainable update to selected layers. The original base weights stay frozen while the added parameters learn.

Base modelExisting weights · frozen
LoRA adapterSmall added weights · trained
Combined modelBase + learned update

Think of the adapter as an adjustment attached to selected calculations inside the model. It is not a text file of facts, and it is not a standalone model. At inference, those calculations use both the original weights and the learned adjustment.

MethodWeights updatedResource implication
Full fine-tuningOriginal model weights, usually across the whole model.Many trainable parameters and optimizer states.
LoRASmall added matrices in selected layers.Fewer trainable parameters and optimizer states; the base model still needs memory.
Our saved adapterOnly the learned addition and its configuration.Load it with the compatible base model to reproduce the behavior.
Optional one-minute math: why “low rank” saves parameters

For a square layer with 1,024 inputs and outputs, a full weight matrix has 1,024 × 1,024 = 1,048,576 numbers. A rank-8 LoRA update uses two matrices with 1,024 × 8 + 8 × 1,024 = 16,384 trainable numbers—about 1.6% as many for that layer. Multiplying the two small matrices forms the update, which is scaled and added to the original weight matrix. This is an illustrative layer, not the measured size of our complete Qwen adapter.

In our script, r=8 sets that rank, lora_alpha=16 scales the update, and q_proj/v_proj identify selected attention projections. You do not need attention mathematics to run the lesson.

Memory matters: freezing the base does not remove it. LoRA reduces training overhead, but a 27B base still needs substantial memory. That is why we use a 0.5B model. This exercise uses bfloat16 LoRA, not QLoRA; QLoRA additionally quantizes the base model.

Ask: “Can I send someone only the adapter and expect it to run by itself?” Answer: No. They also need the compatible base model, tokenizer and software. An adapter may encode sensitive patterns, so it should not be treated as anonymized data.

13–17 minutes · Predict, discuss, check

Give participants one minute to decide, then discuss these questions in pairs. Reveal each answer after hearing their reasoning.

1. The training loss is almost zero. Can we skip testing?

No. Training loss measures prediction of known training answers. Evaluate generated answers on separate development records and, after settings are fixed, a final held-out test.

2. A record omits its department. Should the model guess Maintenance?

No. Our contract requires department: null and includes department in the missing-information list. Learning a common department is not permission to invent one.

3. Which files must survive after training ends?

The saved adapter and its configuration, a compatible base model and tokenizer, and the software environment. Keep dataset/version information and reports too, so you can explain and reproduce the experiment.

4. A document revision changes every week. Train again each week?

Usually begin with authorized local retrieval from the current register, with source references. Fine-tuning is useful for task behavior and format; it is not the default way to maintain changing controlled facts.

17–20 minutes · Optional questions and transition

Ask a volunteer to explain: “Examples teach the adapter; loss guides updates; held-out evaluation checks new answers.” Then move to workstation setup. During training, revisit this section and point to the same steps in scripts/train.py.

Learning check: participants can distinguish training from inference, explain which weights LoRA changes, and say why a saved adapter still needs a base model.

Stage once, then work offline

Offline training requires the model weights, tokenizer and Python packages to be present locally. “Offline” flags prevent Hugging Face downloads; network isolation still belongs to the machine and network configuration.

A. Download the base model on an approved connected machine

python scripts/prepare_model.py

This script resolves a model commit, stores it in models/model-lock.json, and downloads the corresponding files to models/qwen-base/. It never reads the training data. Reruns reuse that revision. Model weights are separate from Ollama’s inference files.

B. For a separate disconnected classroom machine

On a staging machine with the same Linux architecture and Python 3.12, collect wheels for all resolved dependencies. Review transferred packages using your organization’s normal process.

mkdir -p wheelhouse
python -m pip download --only-binary=:all: --dest wheelhouse   --extra-index-url https://download.pytorch.org/whl/cu128   -r requirements-resolved.txt
python scripts/inventory.py create

Transfer this entire folder, including wheelhouse/, models/, requirements-resolved.txt and the inventory. Do not copy the virtual environment between machines. On the disconnected destination:

cd ~/Documents/nuclear-records-workshop
python3 scripts/inventory.py verify
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --no-index --find-links wheelhouse -r requirements-resolved.txt

If working on the same machine, you can skip wheel transfer after staging the model and environment.

C. Enable local-only model loading

export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
export HF_HUB_DISABLE_TELEMETRY=1

Classroom boundary: Use fictional data throughout. A real deployment also needs approved access controls for datasets, adapters, prompts, reports and logs. LoRA is not anonymization, and checksums verify transfer consistency rather than establish software trust.

Read the output
Step loss measures the current example; epoch mean loss averages that epoch’s examples. Lower training loss means the adapter predicts training answers more closely. Development scores tell you whether it handles separate records.


The script saves adapter/, loss.jsonl, run.json and environment.txt under the run folder. Metadata includes seed, model revision when staged with the supplied script, dataset hash, training settings and GPU memory use.
The seed helps repeatability but does not guarantee bit-identical GPU results. An interrupted run is incomplete; use a fresh run directory to restart.

Reload and evaluate the adapter
Evaluation starts a fresh Python process. Loading the saved adapter over the original base model is also your persistence test: the learning must survive after the training process exits.
python scripts/evaluate.py --split dev   --adapter runs/run01/adapter --out runs/run01/dev.json
python scripts/compare.py runs/baseline-dev.json runs/run01/dev.json   --out runs/run01/dev-report.html
Open runs/run01/dev-report.html in your browser. It shows actual scores and expandable records with inputs, targets, baseline responses and adapter responses. All content stays local.
MetricWhat it checks

The test includes missing fields, conflicting document descriptions, and five quoted instructions telling the model to output APPROVED. Inspect those records individually; do not report only an average.


Suggested classroom criteria, chosen before testing: 20/20 valid schemas, at least 18/20 exact answers, no invented departments, and correct handling of all five embedded-instruction cases. These are teaching goals, not operational acceptance criteria. Report baseline and adapter scores whether they pass or fail.


If you revise the model after seeing test errors, that test becomes development evidence. Create a genuinely new held-out set for a new final evaluation. No small test proves general safety or robustness.


Keep the evidence
Archive the chosen adapter, model-lock file, dataset hashes, environment versions, reports and a short decision note. Reports contain input records and outputs; in a real sensitive workflow they inherit the source data’s handling requirements.

Troubleshoot and extend
CUDA is unavailable or the model runs out of GPU memory
Check nvidia-smi, activate this kit’s virtual environment and verify the CUDA PyTorch wheel. Unload local Ollama models. The training script already uses batch size one. Do not upgrade the driver as a first troubleshooting step; your driver and CUDA computation tests already passed.


Offline model files are missing
Check models/qwen-base/config.json, tokenizer files and safetensors weights. Stage the complete model with prepare_model.py on the connected machine and verify the transfer inventory. Do not disable offline loading to conceal a missing transfer.


Output directory or report already exists
Use a new run directory or report filename. For example, --out runs/run03 for training. Prior evidence is preserved intentionally.


JSON is malformed or the model adds prose
Inspect development outputs and the shared prompt. Check that the correct adapter was loaded. Add varied formatting examples to a new training dataset version. Do not modify the scorer to quietly forgive output your downstream application cannot accept.


Training loss falls but test results do not improve
This can indicate overfitting, insufficient coverage or an already strong baseline. Compare fewer epochs on development data and inspect category-specific errors. A tiny synthetic dataset cannot establish broad generalization.


Can we import this directly into Ollama?
This lesson saves a PEFT adapter for Transformers. It does not perform merging, GGUF conversion or Ollama import. First verify the adapter here. Deployment/export is a separate compatibility exercise and should be followed by the same evaluations.
